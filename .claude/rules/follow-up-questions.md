# Follow-Up Questions

Applies to every task (this rule has no `paths`, so it loads at session start).

- Before starting a non-trivial change, ask yourself whether you are confident you understand what is wanted. If you are not, ask targeted follow-up questions first. Aim for roughly 95%+ confidence for changes that touch multiple files or layers.
- Ask only questions whose answers would change what you build: scope, which stack (.NET, Spring Boot, or both), affected layer, expected behavior, or edge cases. Batch them into one short list.
- Offer a recommended default for each question so the user can reply "go with your defaults".
- When you proceed, state your confidence and the assumptions you made in one or two lines.
- Skip the questions for small, unambiguous requests and for explicit lab steps where the prompt already spells out the expected outcome.
